## Purpose and claims

This controlled proof investigates whether the compiler can eliminate redundant bounds checks while preserving the language's bounds-safety rules:

1. A successful explicit `len(b) >= 4` guard can establish safety for the four subsequent fixed-index reads.
2. With no explicit guard, reading `b[3]` before `b[2]`, `b[1]`, and `b[0]` can allow one earlier successful access to establish bounds for subsequent reads. Reading the indices in ascending order does not establish the same information as early.
3. Different compiled check paths may produce a measurable **local** timing difference in a four-byte microbenchmark; this neither isolates bounds checks as the only causal factor nor establishes application-level gains.

`DecodeForward` and `DecodeHighFirst` return the same little-endian `uint32` on valid inputs (`len(b) >= 4`), but may panic at different indices on short inputs. `DecodeGuarded` returns `(0, false)` on short input and is a **mechanism control**, not an equivalent timing competitor.

## Configuration and procedure

The repository's test source uses two separately named benchmarks, `BenchmarkDecodeForward` and `BenchmarkDecodeHighFirst`. Both work on `[]byte{0x12, 0x34, 0x56, 0x78}`, producing `0x78563412`. Both call non-inlined functions, accumulate the same result type, and have no per-iteration allocation intended by the code.

Representative commands (run inside the single `proofs/` Go module):

```powershell
$env:GOTOOLCHAIN = 'go1.26.9'
go version
go build -gcflags='-d=ssa/check_bce/debug=1' ./compiler/bounds-check-elimination

go test -run '^$' -bench '^BenchmarkDecode(Forward|HighFirst)$' `
  -benchmem -benchtime=1s -count=7 ./compiler/bounds-check-elimination
```

The second, order-balanced measurement executed **four consecutive pairs in separate `go test` invocations**, with within-pair order `HighFirst → Forward`, `Forward → HighFirst`, `HighFirst → Forward`, `Forward → HighFirst`; each invocation used `-benchtime=1s -count=1`, `-benchmem`, and a benchmark-specific name filter. This alternation was deliberately added after the initial seven-run blocks showed substantial variation. It reduces, but does not eliminate, time-order confounding.

For machine-code inspection, the experimenter built a Go test binary and ran `go tool objdump` over the two decode symbols and the two benchmark symbols. The supplied assembly text contains these symbols. The full binary and its build metadata were not provided.

## Experiment A/B — Compiler diagnostics

The uploaded `compiler-bce.txt` contains **five** `Found IsInBounds` lines, mapped to the source:

```text
bce.go:26:9: Found IsInBounds
bce.go:27:9: Found IsInBounds
bce.go:28:9: Found IsInBounds
bce.go:29:9: Found IsInBounds
bce.go:40:9: Found IsInBounds
```

| Function | Remaining `IsInBounds` diagnostics | Source locations |
| --- | ---: | --- |
| `DecodeGuarded` | **0** | None reported after the explicit length guard |
| `DecodeForward` | **4** | `b[0]`, `b[1]`, `b[2]`, `b[3]` (lines 26–29) |
| `DecodeHighFirst` | **1** | `b[3]` (line 40) |

`Found IsInBounds` means a bounds check **remains at the compiler's SSA diagnostic stage**, not that the check was eliminated. The explicit `len(b) < 4` guard is still a conditional decision even though `DecodeGuarded` has zero residual *index* checks. These counts are specific to the recorded Go version, target, source, and compiler configuration; they are not CI invariants.

## Machine-code corroboration

Disassembly of the compiled Windows test executable corroborates the diagnostic difference:

| Compiled decode path | Forward | HighFirst |
| --- | ---: | ---: |
| Conditional bounds branches (`JBE`) | **4** | **1** |
| `runtime.panicBounds` call sites | **4** | **1** |
| Data loads on the valid-input path | **One 32-bit `MOVL 0(AX), AX`** | **One 32-bit `MOVL 0(AX), AX`** |

Simplified relevant instruction sequences (not full function listings):

```asm
# DecodeForward
TESTQ BX, BX
JBE   panic
CMPQ  BX, $0x1
JBE   panic
CMPQ  BX, $0x2
JBE   panic
CMPQ  BX, $0x3
JBE   panic
MOVL  0(AX), AX
RET

# DecodeHighFirst
CMPQ  BX, $0x3
JBE   panic
MOVL  0(AX), AX
RET
```

Despite four byte-indexing expressions in the Go source, **both versions compile into a single 32-bit load on the observed successful path**. Thus this experiment is *not* comparing four machine-level byte loads against one load. The notable difference in this build is the additional check-and-branch sequence and panic paths in Forward. Code placement, branches, calling convention, and processor behavior may still affect timing.

The benchmark caller disassembly also shows matching loop structure and an actual `CALL` to the appropriate non-inlined decoder. The order of instructions in the two benchmark bodies is otherwise closely matched, supporting—but not perfectly isolating—the comparison.

The Windows file paths printed in the disassembly include mojibake in non-ASCII directory names. Symbol names, machine instruction bytes, Go source file names/line numbers, and call targets remain legible. This encoding artifact does not prove a problem with the machine code, but the original path text should not be treated as reliable provenance.

## Experiment C — Initial seven-run benchmark

The first run used seven consecutive measurements of Forward followed by seven consecutive measurements of HighFirst, each with the same workload and reported allocation counters.

| Implementation | Seven samples (`ns/op`) | Mean | Median | Sample std. dev. | Range | `B/op` / `allocs/op` |
| --- | --- | ---: | ---: | ---: | --- | --- |
| Forward | 5.370, 4.090, 2.771, 3.617, 3.025, 3.011, 2.079 | **3.423** | **3.025** | 1.067 | 2.079–5.370 | 0 / 0 |
| HighFirst | 2.266, 1.721, 1.715, 1.748, 2.153, 2.015, 1.822 | **1.920** | **1.822** | 0.225 | 1.715–2.266 | 0 / 0 |

Forward varied by more than 2.5× between its fastest and slowest samples. The ordering of whole benchmark blocks and uncontrolled machine conditions are potential confounders. **The initial mean or median difference must not be presented as a stable speedup.** This variability motivated a second, order-balanced measurement rather than selective deletion of inconvenient samples.

## Experiment C — Four alternating-order pairs

All figures below are taken directly from the supplied `bce-order-check.txt`; lower `ns/op` is faster. Each test invocation ran in a separate process.

| Pair | Execution order | Forward (`ns/op`) | HighFirst (`ns/op`) | HighFirst elapsed/op relative to Forward |
| --- | --- | ---: | ---: | ---: |
| 1 | HighFirst → Forward | 1.871 | 1.641 | −12.3% |
| 2 | Forward → HighFirst | 1.820 | 1.500 | −17.6% |
| 3 | HighFirst → Forward | 1.783 | 1.507 | −15.5% |
| 4 | Forward → HighFirst | 1.883 | 1.564 | −16.9% |
| **Mean** | Four pairs | **1.83925** | **1.55300** | **−15.56% using the two means** |

- Forward: median **1.8455 ns/op**; sample std. dev. **0.0464 ns/op**.
- HighFirst: median **1.5355 ns/op**; sample std. dev. **0.0653 ns/op**.
- **All four pairs** measured lower elapsed time for HighFirst, with both invocation orders represented.
- Every observation reported **0 B/op and 0 allocs/op**.

The 15.56% figure describes **lower elapsed nanoseconds per operation in these four pairs**, calculated as `(mean(Forward) − mean(HighFirst)) / mean(Forward)`. It is neither a confidence interval nor a claim about universal service throughput. Four paired measurements are modest evidence; they do not fully control CPU frequency, thermal state, scheduling, benchmark calibration, or independent process effects. The observed code-generation difference is a plausible explanation, **not a proof that BCE alone caused the full timing difference**.

## Caveats and interpretation

1. **Safety is preserved.** The compiler can eliminate redundant checks where it establishes valid bounds; it does not turn out-of-range indexing into defined memory access. Guarded has a different short-input contract; Forward and HighFirst can panic at different points on invalid inputs.
2. **SSA checks are not final branch counts.** This case has both SSA diagnostic and disassembly evidence; other compiler versions or targets may show different lowering or optimization.
3. **No inlining in the experiment.** `//go:noinline` deliberately excludes caller-specific information; the result cannot characterize every normal inlined production call site.
4. **Nanosecond-scale measurements are sensitive to the test machine.** The initial benchmark was quite variable. The alternating-order data are more coherent, but no measured CPU frequency, temperature, pinning, or hardware-counter trace was supplied.
5. **Microbenchmark ≠ end-to-end win.** Even a consistent local reduction does not demonstrate a meaningful change to service throughput, P99 latency, energy use, or real parser performance.
6. **Provenance limits.** The experiment revision is recorded, but a clean working tree and exact benchmark executable identity were not independently established by captured build metadata; the compiler-output and assembly files must remain associated with their external source archive.

## Conclusion

**Mechanism verified on Windows Go 1.26.9.** The two unguarded four-byte decoders produced **four versus one** remaining SSA bounds checks, corroborated by **four versus one** machine-code branch/panic paths; the guarded decoder had zero residual SSA index checks. Both unguarded decoders compiled to a single four-byte data load on the successful path.

In four alternating-order benchmark pairs, HighFirst measured **1.55300 ns/op** on average compared with **1.83925 ns/op** for Forward (approximately **15.6% less measured time per operation** in this specific run), with no reported per-operation allocations. The initial seven-run blocks were considerably noisier. These results are **local performance observations**, not a general optimization recommendation or a demonstration of the isolated cost of exactly three bounds checks.

**Classification: Compiler mechanism verified; local Windows cost observed and qualified; production impact untested; Linux reproduction pending.**
