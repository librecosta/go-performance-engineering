## Purpose

Reproduce the three-case BCE proof under a second execution environment:

1. `DecodeGuarded` uses an explicit `len(b) >= 4` contract, potentially eliminating later per-index checks while preserving its guard.
2. `DecodeForward` reads indices 0, 1, 2, 3; `DecodeHighFirst` reads 3, 2, 1, 0. Both return the same little-endian `uint32` for inputs with `len(b) >= 4`, but can panic at different indices for shorter inputs.
3. Compare *local* runtime cost with the same valid four-byte input and symmetric benchmark harnesses, without treating timings as production speedup or attributing all differences exclusively to BCE.

All three decoders are compiled with `//go:noinline`; inlining is deliberately disabled only for those functions, without disabling ordinary compiler optimizations globally.

## Execution procedure

Commands shown below summarize what **actually ran** in the sandbox. The test binary was copied to a temporary experiment directory outside any Git working tree; no Go compilation was performed on Linux.

```bash
export GOMAXPROCS=4
./bce-linux.test -test.v -test.run '^TestDecode' -test.count=1 -test.timeout=20s

# Seven consecutive benchmark runs per implementation, in one process.
./bce-linux.test -test.run '^$' \
  -test.bench '^BenchmarkDecode(Forward|HighFirst)$' \
  -test.benchmem -test.benchtime=1s -test.count=7 -test.timeout=2m

# For each of four alternating-order pairs, launch a NEW test process for each mode.
./bce-linux.test -test.run '^$' -test.bench '^BenchmarkDecodeHighFirst$' \
  -test.benchmem -test.benchtime=1s -test.count=1 -test.timeout=40s
./bce-linux.test -test.run '^$' -test.bench '^BenchmarkDecodeForward$' \
  -test.benchmem -test.benchtime=1s -test.count=1 -test.timeout=40s
# Swap order on pairs 2 and 4; pairs 1 and 3 run HighFirst first.

# Disassembly performed using the sandbox's local Go 1.23.2 objdump frontend.
go tool objdump -s 'DecodeForward|DecodeHighFirst|BenchmarkDecodeForward|BenchmarkDecodeHighFirst' ./bce-linux.test
go tool objdump -s '^github.com/librecosta/go-performance-engineering/proofs/compiler/bounds-check-elimination.DecodeGuarded$' ./bce-linux.test
```

`timeout` also bounded each external process; no timeout occurred. The initial block may be confounded by its fixed variant order. All four subsequent pairs used the prescribed AB/BA alternation in **separate test processes**.

## Experiment A — Correctness verification

`TestDecodeValid` **PASS** for seven explicit input cases: known bytes, trailing bytes, zero, all bits set, low byte, high byte, and alternating bits.

`TestDecodeShort` **PASS** for nil, empty, 1-, 2-, and 3-byte slices, and a short slice with spare capacity. Guarded returned `(0, false)` for short input; Forward and HighFirst both panicked as expected, without asserting panic-message equivalence.

All tests completed with `PASS`. No race-detector, application-level workload, or sanitizer results are claimed.

## Experiment B — Compiler diagnostics and machine code

The supplied **Linux-target Go 1.26.9** compiler diagnostic file reports five residual `Found IsInBounds` entries, all in `bce.go`: four at lines 26–29 (Forward) and one at line 40 (HighFirst).

| Function | Residual SSA `IsInBounds` | Machine-code observation |
| --- | ---: | --- |
| `DecodeGuarded` | **0** | Explicit `len` comparison and branch remain; then one 32-bit load on valid input |
| `DecodeForward` | **4** | Four conditional `JBE` branches and four `runtime.panicBounds` call sites |
| `DecodeHighFirst` | **1** | One conditional `JBE` branch and one `runtime.panicBounds` call site |

`Found IsInBounds` means the compiler **retained** a bounds check at the reported SSA stage, not that an elimination was recorded. Zero *residual index checks* in Guarded does **not** imply removal of its explicit length-validation branch.

Relevant Linux disassembly excerpts (edited for readability, not reproducing full prologues/addresses):

```asm
# DecodeForward — four check-and-branch sequences
TESTQ BX, BX
JBE   panic
CMPQ  BX, $0x1
JBE   panic
CMPQ  BX, $0x2
JBE   panic
CMPQ  BX, $0x3
JBE   panic
MOVL  0(AX), AX
RET

# DecodeHighFirst — one check-and-branch sequence
CMPQ  BX, $0x3
JBE   panic
MOVL  0(AX), AX
RET

# DecodeGuarded — explicit guard, not a bounds-panic path
CMPQ  BX, $0x4
JGE   valid_input
# short-input return
valid_input:
MOVL  0(AX), AX
RET
```

Both unguarded decoders' valid-input paths contain **one 32-bit `MOVL 0(AX), AX` data load**, despite four indexed byte reads in Go source. They are not four loads versus one load in the final code. The benchmark caller disassembly shows symmetric `testing.B.Loop` structures and actual calls to the respective out-of-line functions. The primary visible difference in these decoder bodies is the residual bounds-check and panic path sequence. This is a plausible cause of runtime differences but is **not** an isolated causal measurement of bounds checks alone.

## Experiment C — Initial seven-run benchmark

Go's testing harness ran Forward seven times consecutively, then HighFirst seven times. All 14 samples reported **0 B/op and 0 allocs/op**.

| Implementation | Seven raw `ns/op` observations | Mean | Median | Sample SD | Range |
| --- | --- | ---: | ---: | ---: | --- |
| Forward | 1.763, 1.746, 1.854, 1.824, 1.760, 1.873, 2.166 | 1.855 | 1.824 | 0.146 | 1.746–2.166 |
| HighFirst | 1.640, 1.489, 1.476, 1.479, 1.542, 1.485, 1.513 | 1.518 | 1.489 | 0.059 | 1.476–1.640 |

Forward's last measurement was **2.166 ns/op**, above the rest of its block. HighFirst's values were more concentrated. These run blocks do not balance execution order; the initial mean difference should not be presented as a general speedup.

## Experiment C — Four alternating-order pairs

Each benchmark invocation ran in a **new Linux process**; within-pair order alternated HighFirst-first / Forward-first. Every observation again reported **0 B/op and 0 allocs/op**.

| Pair | Execution order | Forward (`ns/op`) | HighFirst (`ns/op`) | HighFirst elapsed/op vs. Forward |
| --- | --- | ---: | ---: | ---: |
| 1 | HighFirst → Forward | 1.822 | 1.457 | −20.0% |
| 2 | Forward → HighFirst | 1.767 | 1.440 | −18.5% |
| 3 | HighFirst → Forward | 1.751 | 1.539 | −12.1% |
| 4 | Forward → HighFirst | 1.795 | 1.520 | −15.3% |
| **Mean** | 4 pairs | **1.78375** | **1.48900** | **−16.52% (ratio of means)** |

- Forward median: **1.7810 ns/op**, sample SD **0.0313 ns/op**.
- HighFirst median: **1.4885 ns/op**, sample SD **0.0479 ns/op**.
- All four pairs showed lower measured `ns/op` for HighFirst, in both invocation orders.
- The **16.52%** figure is `(mean(Forward) − mean(HighFirst)) / mean(Forward)`, an observed *local elapsed-time reduction*, not a confidence interval or application-throughput gain.

These four pairs are modest evidence and cannot eliminate noise from virtual CPU scheduling, cgroup throttling, process startup, power/frequency policy, benchmark calibration, or hypervisor activity. The result is consistent with—but does not prove an exclusive causal effect from—the observed machine-code difference.

## Limitations and recommendations

1. **Source provenance is qualified:** the executable hash and Go build information are verified; the commit SHA comes from the supplied manifest, with a reported untracked reports directory. No embedded `vcs.revision` or clean-tree evidence independently confirms the binary came from exactly that commit. Avoid claiming otherwise.
2. **Compiler evidence differs in origin:** `check_bce` was run by the experimenter on Windows targeting Linux; the correctness tests, CPU execution, and disassembly were reproduced on the Linux sandbox.
3. **`//go:noinline` is a deliberate experimental control:** an inlined production call may generate different checks and different costs.
4. **Failure semantics differ:** Forward and HighFirst return the same result on legal inputs, but may panic with different details for short inputs. Guarded has an explicitly different `(value, bool)` failure contract.
5. **Benchmarks are narrow:** these hot-loop nanosecond-scale observations exclude realistic parsing chains, request work, contention and latency distributions; CPU percentages cannot be generalized.
6. **Machine code is stronger evidence than check counts alone:** SSA residual-check counts do not imply machine-branch counts in arbitrary targets; here both are independently inspected on Linux.
7. **No tuning prescription:** do not routinely reverse reads or add obscure proof tricks without representative profiling and end-to-end validation. Prefer clear length guards and maintainable code.

## Conclusion

**Compiler mechanism verified on Linux Go 1.26.9.** Forward retained four SSA index checks and four machine-code bounds branches/panic call sites; HighFirst retained one of each. Guarded retained no extra index checks after its explicit length guard. For both unguarded decoders, the valid-input machine code performed one 32-bit data load.

In four order-alternating benchmark pairs, Forward averaged **1.78375 ns/op** and HighFirst **1.48900 ns/op**: **16.52% less observed elapsed time per operation** for HighFirst, with 0 B/op and 0 allocs/op. This is a controlled synthetic-local observation under a virtualized CPU quota, not an isolated price for exactly three checks and not a general production recommendation.

**Classification: Mechanism reproduced in two environments; local performance differences observed with documented measurement and provenance limits; production impact untested.**
