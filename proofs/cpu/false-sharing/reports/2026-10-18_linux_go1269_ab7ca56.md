## Research question and controlled layout

Can two goroutines updating separate atomic counters incur an extra execution cost merely because their counter addresses share a cache line, and does that cost change when `GOMAXPROCS` permits parallel execution?

- Both cases allocate the same 23-element `[]atomic.Uint64` backing storage and select the first actual 64-byte-aligned, 16-element (128 B) window.
- Packed uses counter offsets 0/8 B (same 64 B line); Separated uses offsets 0/64 B (different lines). The code checks actual address alignment and line relationship for every benchmark allocation; it does not infer line ownership from Go type size alone.
- Exactly two goroutines invoke the **same** `atomic.Uint64.Add(1)` update loop. Each writes only one independent counter. A synchronized release follows worker readiness. Final counts must both equal 80 million; the benchmark stops its timer before verifying them.
- `b.N` is **total** updates by both workers. Therefore `ns/op` is timed wall-clock nanoseconds divided by 160 million aggregate updates (not per-worker instruction latency), and `updates/s = 10^9 / (ns/op)` without a factor of two.
- `GOMAXPROCS=1` prevents the workers from executing user Go code simultaneously but is not CPU pinning. `GOMAXPROCS=2` allows parallelism but does not establish separate physical-core residency.

## Verification and measurement procedure

**Artifact verification.** Uploaded ZIP entries were checked against the original `checksums.sha256`: the ELF, `build-info.txt`, and `go-version-m.txt` all matched. The extracted binary was identified by `file` as x86-64 statically linked ELF. The sandbox verified `go version -m`, execution permissions, Debian/kernel/CPU information, CPU quota, memory limit and sysfs cache-line sizes before running.

**Correctness.** The following tests all passed on the Go 1.26.9 Linux target binary, including layout, even/odd update counts, and invalid preconditions:

```bash
./false-sharing-linux.test -test.run '^TestFalseSharing' -test.v -test.count=1
```

**Calibration (excluded from formal statistics).** At `GOMAXPROCS=1`, Separated measured 2.257 ns/update with N=10,000,000 and 2.180 ns/update with N=160,000,000 (about 0.349 seconds timed). Based on the frozen 0.3–1.0-second target, we chose **N=160,000,000** for all Linux formal cases and never changed it mid-series.

**Preflight protocol note.** The frozen design requested a short smoke at both P=1 and P=2 before formal measurement. This campaign ran correctness tests and P=1/Separated calibrations, but did **not** run a separate short P=2 smoke before the formal sequence. The subsequent P=2 formal samples themselves all passed layout, update-count, benchmark-identity, exit-status and `GOMAXPROCS` checks. We retain this minor preparation-order deviation in the audit rather than retroactively claiming the preflight was complete.

**Formal invocation.** Every sample launched the same precompiled ELF in a new process; the environment set `GOMAXPROCS` to 1 or 2, and only one exact benchmark name was selected. For example:

```bash
GOMAXPROCS=2 ./false-sharing-linux.test -test.run '^$' \
  -test.bench '^BenchmarkFalseSharingPacked$' \
  -test.benchtime=160000000x -test.count=1
```

The same command selected `Separated` and P=1 as required. Round 1 ran P1→P2 with ABBA, round 2 P2→P1 with BAAB, and rounds 3–4 repeated the alternation. This yields **32 independent OS processes; 8 per cell; 8 adjacent pairs per P**. The `b.N=1` detail line that appears in stdout is a benchmark harness probe, not an extra formal measurement.

**Integrity results.** All 32 child processes exited successfully with `PASS`; each reported exactly 160,000,000 formal updates, 80,000,000 per worker, correct benchmark identity and actual `GOMAXPROCS`, and empty stderr. The independent post-run audit checked every CSV row against raw stdout. No timed sample was rejected, removed as an outlier, re-run in isolation, or replaced by a calibration run.

### Interpretation

With P=1, the two layouts have similar median execution costs (2.2140 versus 2.2020 ns/update). Across P=2, Packed took 4.4570 ns/update versus 1.1140 for Separated. All eight P=2 adjacent pairs favored Separated, including the reversed BAAB ordering; the relative layout effect was much larger than at P=1. The P=2 Packed observations varied from 4.190 to 5.691 ns/update; all were retained and reported.

**Classification: the Linux synthetic workload exhibits a strong, reproducible parallel layout effect consistent with false sharing under the tested conditions.** The direct physical coherence mechanism is supported by established hardware principles, but this experiment does **not** count cache-to-cache transfer / HITM events or measure core placement.

## Windows comparison — mechanism direction, not machine ranking

The previously archived Windows Go 1.26.9 study used the same proof source blob and N=160 million updates per process, on Ryzen 7 5800H / Windows 10, and reported the following **within-machine** paired ratios. The Windows values below are taken from that separate Windows Report; they are not remeasured on Linux.

| Measure | Windows (prior report) | Linux (this report) |
| --- | ---: | ---: |
| P=1 paired Separated/Packed throughput ratio, median | 1.003× | 1.025× |
| P=2 paired Separated/Packed throughput ratio, median | 11.190× | 4.074× |
| Corresponding-pair median interaction `R₂/R₁` | 11.170× | 4.134× |

Both operating environments have near-equal layout performance at P=1 and a consistently higher Separated throughput at P=2. **Only the direction of the controlled mechanism is replicated across environments.** The relative effect magnitude differs; scheduler behavior, virtualization, hardware cache coherence, CPU topology, and execution conditions may all contribute. This experiment does not identify which factor caused the cross-system difference. Do not compare absolute ns/op across machines as a CPU or OS performance ranking.

## Limitations and evidence boundaries

1. **No direct hardware event sampling.** There are no `perf c2c`, PMU HITM, cache-to-cache transfer or physical-core residency measurements. Verified virtual address placement plus the P=1/P=2 layout interaction are *indirect* mechanism-compatible evidence.
2. **Virtualized, quota-constrained execution.** Five visible virtual CPUs with a four-CPU-equivalent cgroup quota do not guarantee stable placement on distinct physical cores. Host contention, scheduling migration, SMT, frequency behavior and CPU entitlement can alter observed costs.
3. **Timing scope.** Each timed region includes release of a shared starting gate, goroutine scheduling/wakeup and final wait. Setup, allocation, final count verification and result logging are excluded; fixed overhead has not been independently measured as zero.
4. **Synthetic atomic-heavy path.** Two workers repeatedly mutate only two hot counters. Real applications may update them much less often, combine increments, read more frequently, or have a layout/memory-footprint trade-off that makes padding counterproductive.
5. **Measurement variability.** Printed `ns/op` values are rounded, and P=2 Packed times varied noticeably across the 8 samples. We retained all results. No arbitrary effect-size threshold, statistical significance claim or production-benefit inference was used.
6. **Provenance.** The Windows manifest identifies the source revision/blob, and the Linux binary is identified by a verified SHA-256, but missing embedded VCS revision prevents independent ELF-to-commit attestation. The sandbox did not rebuild with its older Go compiler.
7. **Resource metrics differ.** Cache line size is corroborated by sysfs; process RSS, GC traffic, QPS, P95/P99 and energy use were not measured. `ns/update` is not an individual instruction latency estimate.

## Conclusion

**Linux Go 1.26.9 reproduction succeeded under the frozen experimental contract.** All 32 formal runs were valid. At `GOMAXPROCS=1`, the Separated/Packed paired throughput ratio median was **1.025×**. At `GOMAXPROCS=2`, the same ratio median was **4.074×** (range **3.801–4.766×**), with no reversal of the P=2 layout result across adjacent pairs or measurement-order alternation. The two-platform direction matches the prior Windows observation, while effect magnitude remains environment-sensitive.

**Final classification: layout and correctness verified; local performance effect reproduced across Windows and Linux under documented workloads; direct coherence traffic and application-level benefits untested.**
