## Claim and scope

With two goroutines updating independent atomic counters in a fixed workload, putting both counters in one 64-byte cache line may impose coherence-related cost under parallel execution. Separating them into different lines should reduce that cost if false sharing is a material bottleneck. The experiment tests the **local runtime-cost interaction** between memory layout and permitted parallelism; it is not a direct hardware cache-to-cache measurement.

## Design and controls

- The two layouts use identical underlying storage types: a 23-element `[]atomic.Uint64`, with a selected 64-byte-aligned, 16-element / 128-byte window. The benchmark validates the addresses anew for its own allocation.
- Packed uses offsets `A=0 B=8` bytes (same 64-byte line). Separated uses `A=0 B=64` bytes (different 64-byte lines). No padding bytes are written; both modes call the same update loop.
- Two fixed workers each perform 80 million atomic updates. The start channel is released after the workers have announced readiness; the timer stops when both finish. Allocation, setup, worker creation and final count verification are excluded; release/wakeup and final completion-wait overhead remain included.
- `b.N` means **aggregate updates across both workers**. Therefore `ns/op` is total timed wall-clock nanoseconds divided by 160 million aggregate updates; it is not latency per worker or CPU cycles per update. Aggregate updates/s is `1e9 / (ns/op)` with **no extra factor of two**.
- `GOMAXPROCS=1` prevents simultaneous execution of user Go code by the two workers, but does not pin the process to one physical core. `GOMAXPROCS=2` permits parallelism, without proving that workers were always on separate physical cores.
- The `100000x` fixed-iteration preflight succeeded. Each of the 32 formal runs used a fresh scripted child invocation and exactly `160000000x`, one selected benchmark, and `-test.count=1`. The `b.N=1` line in each stdout is a benchmark harness probe, not an extra formal sample.
- The previous script revision failed its first iteration-count check and its output was excluded; all observations here came from the corrected campaign with the fixed-iteration preflight.

- **Parallelism × layout interaction:** matching pairs by round and pair position, the median `R_2 / R_1` is **11.170×**, range **10.470–11.519×** across eight corresponding pair indices. This is a descriptive interaction measure, not an estimate of hardware transfer events.

### Interpretation

Under P=1, the two layouts are nearly indistinguishable at this workload scale: their cell median times are 1.8665 and 1.8605 ns/update, and the paired ratio median is approximately 1.003×. Under P=2, Separated measures about 0.934 ns/update while Packed measures about 10.45 ns/update; the eight P=2 paired ratios are all between 10.638× and 11.532×. The P=2 layout effect is consistently far larger than the P=1 layout effect, including when ABBA order and the P-group order reverse.

This **strongly supports a local performance effect consistent with false sharing under the tested conditions**. It does not independently measure HITM events, cache-line ownership transfers, core residency, exact CPU frequency, or temperature. In particular, it would be overclaiming to interpret the roughly 11× relative throughput ratio as an 11× reduction in coherence traffic or as a universal Go application speedup.

## Caveats and evidence limits

1. **No direct hardware-counter proof.** `perf c2c`, PMU HITM counters, and CPU-affinity controls were not part of the frozen first Proof. Cache-line placement is verified relative to the documented 64-byte model, but actual cache-line transfers are not measured.
2. **Goroutine scheduling is uncontrolled.** `GOMAXPROCS=2` permits rather than guarantees sustained simultaneous execution on separate physical cores. SMT placement, OS migration, frequency changes, and interrupt load may influence the size of the measured effect.
3. **Synthetic hot loop.** Both workers repeatedly update one counter with an atomic read-modify-write operation. A real Go service with reads, batching, infrequent updates, or different allocation/layout patterns may behave very differently.
4. **Benchmark includes synchronization boundary costs.** The timed region contains start-channel release and final wait in addition to atomic updates. With N=160 million these fixed costs are likely small relative to the repeated hot work, but they have not been isolated as zero.
5. **Different cell durations.** A fixed N was selected from the P=1/Separated precheck, as required by the frozen contract. The P=2/Separated measurement region was about 0.15 s, whereas P=2/Packed was about 1.6–1.7 s; no post-hoc change to N was made.
6. **Single machine and time window.** Results come from one Ryzen 7 5800H on Windows 10, a short measurement session, and one Go 1.26.9 binary. Do not infer a production throughput or P99 benefit, or make a cross-OS performance ranking.
7. **Build provenance boundary.** `source_clean=true` and the commit ID are preserved from the script manifest. The archived executable does not embed an independently verifiable VCS revision, so a precise clean-revision-to-binary identity cannot be established from build metadata alone.
8. **Reported precision.** Ratios are recomputed from the `ns/op` values printed by Go; they inherit rounding in the original benchmark stdout and should not be represented as high-precision hardware measurements.

## Conclusion

**Classification: Windows local-layout effect reproduced across eight independent adjacent pairs per P; performance evidence strongly consistent with false sharing; direct cache-coherence-event verification and production impact untested.**

The frozen two-worker test showed little layout difference at `GOMAXPROCS=1` but a large and consistent relative throughput difference at `GOMAXPROCS=2`. The P=2 paired Separated/Packed throughput ratio had a median of **11.190×** (range **10.638–11.532×**); the P=1 median ratio was **1.003×**. This does not justify general-purpose padding recommendations without measuring realistic application access patterns and memory costs. Linux should next test whether the **mechanism-compatible direction** reproduces; absolute timing and ratio magnitude should not be expected to match Windows.
