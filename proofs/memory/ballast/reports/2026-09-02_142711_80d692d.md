## Purpose

Verify that, under GOGC-based pacing and without a binding runtime
memory limit, a long-lived heap ballast:

1. materially increases the live heap after the setup GC;
2. materially increases the next GC heap goal;
3. materially reduces GC cycle frequency for the same allocation-churn workload.

This report verifies the historical heap-ballast mechanism.

It does not attempt to establish heap ballast as a recommended modern
Go optimization.

## Performance Observation

Wall-clock elapsed time is intentionally observational and is not part
of the proof's pass/fail contract.

The three manual pairs produced:

```text
Run 1: ballast ~12.3% slower
Run 2: ballast ~5.5% faster
Run 3: ballast ~17.3% slower
```

Manual means:

```text
Baseline: 40.07 ms
Ballast:  42.93 ms
```

This is not sufficient evidence for a stable wall-clock improvement.

The automated child-process runs happened to show lower elapsed time
with ballast in all three runs, but that result should also not be
treated as a universal performance claim.

This divergence is useful evidence for the proof methodology itself:

> A strongly reproduced runtime mechanism does not imply a stable
> wall-clock speedup on every short benchmark run.

GC pause observations were lower in the ballast cases in this test,
including two runs reporting `0s`. Pause time remains observational
here and is not used as a correctness or performance assertion.

## Interpretation

The experiment clearly proves that heap ballast changes GOGC-based
pacing.

It does **not** prove that heap ballast makes this synthetic workload
consistently faster in elapsed wall-clock time.

That distinction is intentional.

The mechanism evidence is substantially stronger than the timing
evidence:

```text
Mechanism:
strong and repeatable

Wall-clock performance:
noisy and inconclusive in the manual runs
```

This is exactly why the automated proof asserts heap/pacer behavior
instead of elapsed time.

## Caveats

### Go version

This report was produced with:

```text

```

The repository currently treats Go 1.27 as its primary baseline, so a
later Go 1.27 revalidation should be stored as a separate report rather
than overwriting this one.

### Working tree

The working tree was not clean during environment capture because the
six JSON result files were untracked.

No source-code modifications were reported by `git status --short`.

### Synthetic workload

The workload deliberately produces a small live working set and high
short-lived allocation churn.

It is designed to make the pacing mechanism obvious, not to model a
production service.

### Historical recommendation

Heap ballast is a historical technique.

Modern Go applications should normally express GC and memory policy
through supported runtime controls such as GOGC and GOMEMLIMIT and
validate those settings using representative workloads.
