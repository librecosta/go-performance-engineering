# Heap Ballast Proof Report (Linux)

## Metadata

- Experiment date: **2026-10-14**, around 15:48–15:50 UTC (23:48–23:50 +08:00).
- Repository: `librecosta/go-performance-engineering`, `dev` branch.
- Experiment source revision: `dab084e0fd8d4b208cb1b317702643372d262a25` (embedded `vcs.revision`); main binary reports **`vcs.modified=false`**.
- Compiler and runtime: **Go 1.26.9**, cross-compiled on Windows for `linux/amd64`, `CGO_ENABLED=0`, `GOAMD64=v1`. Verified using the Go binary build information and all ten JSON results.
- Sandbox: Debian GNU/Linux 13 (trixie), Linux kernel `6.18.44`, x86_64.
- CPU: AMD EPYC 9V74 80-Core Processor under virtualization; 5 visible logical CPUs; cgroup quota **4 CPU-equivalents** (`cpu.max=400000 100000`).
- Memory: 4 GiB cgroup cap (`memory.max=4294967296` bytes).
- Execution environment: `GOMAXPROCS=4`; external `GOGC`, `GOMEMLIMIT` and `GODEBUG` unset. The proof explicitly sets `GOGC=100` and a non-binding runtime memory limit internally.
- Main executable SHA-256: `bfd38bc735f7fafe2db469cf68207caa8266fd1b34eaaf3b3ef91a92f393993a`.
- Test executable SHA-256: `cebcc9e502653d613a28ec54a6fd632b5c7dbb77a3073bb029055beebec24467`.
- Raw evidence: 10 machine-readable JSON files, repeated automated test output, build/environment information, and SHA-256 manifest in a separate evidence archive.

## Purpose

Reproduce the **historical GOGC-based heap-ballast mechanism** in a Linux environment, using the same workload configuration as the preserved Windows historical report (but a different Go patch version).

The controlled claims are: a long-lived 64 MiB pointer-free allocation increases the live heap after setup GC, increases the next GC goal, and reduces GC cycle frequency under a fixed 256 MiB short-lived allocation churn workload.

**This is not a recommendation to use heap ballast in modern production services.** Fewer GC cycles do not by themselves establish improved application-level performance.

## Configuration and procedure

| Parameter | Value |
| --- | --- |
| Ballast | `0 MiB` (baseline) or `64 MiB` |
| Allocation churn | `256 MiB` |
| Allocation block | `8 KiB` |
| Batch size | `64` |
| GC policy | `debug.SetGCPercent(100)` |
| Runtime memory limit | `debug.SetMemoryLimit(math.MaxInt64)` (non-binding) |
| Independent processes | 5 for each mode (10 total), interleaved by pair |
| Metrics | HeapAlloc after setup GC, NextGC, GC cycles, GC pause, total allocated, elapsed, checksum |

The supplied Go 1.26.9 Linux binaries were built with the shared Proof module. The sandbox ran the binaries directly; no recompilation with its older installed Go version was performed. Every manual run launched a **fresh OS process**. Run order alternated across pairs (`baseline → ballast` for runs 1, 3, 5; `ballast → baseline` for runs 2, 4) to reduce order bias.

Commands, from a directory containing the uploaded binaries:

```bash
export GOMAXPROCS=4
./ballast-tests-linux -test.v -test.run '^TestBallastMechanism$' -test.count=3 -test.timeout=3m
./ballast-linux -ballast-mib=0  -churn-mib=256 -block-kib=8 -batch=64 -json > baseline-1.json
./ballast-linux -ballast-mib=64 -churn-mib=256 -block-kib=8 -batch=64 -json > ballast-1.json
```

Equivalent commands were repeated with unique filenames for runs 2–5. The separate-process experiment allocates and initializes the ballast (if any), triggers setup GC, snapshots `HeapAlloc` and `NextGC`, then measures the allocation-churn phase only. The runtime uses `runtime.KeepAlive(ballast)` to make the ballast lifetime explicit.

## Performance observation

The five manual runs recorded a mean churn-phase elapsed time of **66.162 ms** without ballast and **48.455 ms** with ballast. This is a **26.8% lower observed mean** in this specific Linux sandbox and workload; all five paired ballast runs had a lower elapsed measurement.

However, the reported elapsed time **excludes ballast construction and the forced setup GC**. The experiment is synthetic, only five run-pairs were collected, and the shared virtualized environment introduces CPU scheduling variability. The value is an observation, not an unconditional or statistically established application performance improvement.

GC pause in churn is also lower in this local Linux experiment; it is cumulative pause time, not a complete accounting of GC CPU cost or tail latency. No heap RSS or end-to-end service metric was measured.

## Comparison with the preserved Windows historical report

The separately preserved **2026-09-02 Windows / Go 1.26.7** report used 0/64 MiB ballast, 256 MiB churn, 8 KiB blocks, batch size 64, and three manually observed run-pairs.

| Metric | Windows (Go 1.26.7, 3 pairs) | Linux sandbox (Go 1.26.9, 5 pairs) |
| --- | ---: | ---: |
| Baseline mean GC cycles | 92.33 | 85.00 |
| Ballast mean GC cycles | 4.00 | 4.00 |
| GC-cycle reduction | ~95.7% | ~95.3% |
| Baseline mean elapsed | 40.07 ms | 66.162 ms |
| Ballast mean elapsed | 42.93 ms | 48.455 ms |

**Cross-environment conclusion:** both reproduce the GOGC heap-goal / GC-frequency mechanism. Their timing observations differ: the historical Windows manual runs did not establish a repeatable speedup, whereas all five Linux run-pairs were faster in the measured churn phase. These were **not identical-toolchain, identical-hardware A/B trials**: OS, CPU scheduling/virtualization and Go patch version differ. Do not attribute the observed timing difference to a single cause or rank the two machines.

The original Windows report is historical evidence and remains unchanged; the Linux report does not retroactively revise its measurements.

## Caveats

1. **Historical technique, not modern advice.** Ballast adds intentionally live memory, affecting GOGC pacing, but is not a general-purpose tuning knob. Modern applications should first consider supported `GOGC` and `GOMEMLIMIT` policies under representative workloads. `GOMEMLIMIT` is not the same mechanism as ballast.
2. **The memory budget matters.** This Proof deliberately sets the runtime memory limit to non-binding, so it does not model a service constrained by a realistic `GOMEMLIMIT` / tight container memory budget. Ballast is not free memory.
3. **Workload specificity.** The allocation churn is 256 MiB of short-lived 8 KiB buffers retained in small batches. Behavior and timing can differ for pointer-rich objects, large live heaps, or real request traffic.
4. **Timing scope.** Churn elapsed excludes initial ballast allocation, setup GC, and total process lifetime. Reduced GC frequency does not alone demonstrate reduced latency, total CPU, or cost.
5. **Virtual environment.** The execution environment has a four-core cgroup CPU quota despite more logical CPUs being visible. Measurements may vary with shared host load.
6. **Version provenance.** Linux uses Go 1.26.9; the historical Windows experiment used Go 1.26.7. The binary reports a clean source revision, but the uploaded test executable does not independently embed an equivalent VCS revision field; both submitted files have archived checksums.
7. **Metrics differ.** `HeapAlloc`, `NextGC`, GC cycle counts, cumulative GC pause, churn elapsed, and RSS answer different questions. This report does not infer process RSS from heap goal or claim production improvements.

## Conclusion

**Mechanism verified on Linux Go 1.26.9.** The synthetic 64 MiB heap ballast increased live heap and raised the next GC goal from 4 MiB to approximately 128.38 MiB, reducing churn-phase GC cycles from an average of 85 to 4. The same mechanism had been observed in the archived Windows Go 1.26.7 experiment.

In this particular Linux sandbox, the measured churn phase was also faster with ballast. Unlike the historical Windows observations, this is consistent within the five run-pairs; nevertheless it is not enough to recommend heap ballast as a modern production optimization.

**Classification: Historical mechanism reproduced across two environments. Local performance observations are environment-dependent. Production benefit untested.**
