## Purpose

Confirm on a second execution environment that:

1. A 100-byte slice view keeps its 100 MiB backing array reachable.
2. Full slice syntax `src[:100:100]` restricts capacity but does not release the source array.
3. An independent copy allows the large source allocation to become unreachable once no other owner retains it.
4. A copy entails measurable time and allocation costs, distinct from long-lived retained heap.

This is a mechanism proof plus microbenchmark, **not** a production throughput/SLA measurement.

## Configuration and procedure

Each retention mode is executed by an independent Linux process. The CLI initializes the 100 MiB source inside `makeResult`, retains only the returned prefix through a controlled global root, and collects the `baseline`, `retained`, and `released` heap snapshots. Each snapshot invokes two explicit GCs before reading runtime heap statistics. An `inuse_space` heap profile is written while the prefix is reachable, before releasing the root.

Representative commands from the extracted binaries directory (repeat for `view`, `cap`, `copy` and runs 1–3):

```bash
export GOMAXPROCS=4
./retention-tests-linux -test.v -test.run '^Test' -test.count=1 -test.timeout=2m
./retention-linux -mode view -size-mib 100 -keep-bytes 100 \
  -profile results/profiles/view-1.heap.pprof > results/view-1.json
go tool pprof -top -inuse_space results/profiles/view-1.heap.pprof \
  > results/text/view-1.pprof.txt
```

Formal local operation benchmark:

```bash
./retention-tests-linux -test.run '^$' -test.bench '^BenchmarkPrefix$' \
  -test.benchmem -test.benchtime=1s -test.count=5 \
  -test.timeout=10m -bench-size-mib=100 > results/benchmark-linux.txt
```

All commands ran without correctness failures or oversized-memory errors. The bundled test executable was not rebuilt on the sandbox and the benchmark uses the same source and compiler as the CLI executable in this package.

## Experiment A/B — Retained heap

All values are `retained.heap_alloc - baseline.heap_alloc` within each process, in **MiB**, computed from the raw integer-byte JSON fields (not cross-process absolute heap totals):

| Mode | Run 1 | Run 2 | Run 3 | Mean | `len` | `cap` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| View (`src[:100]`) | 100.00509 | 100.00011 | 100.00509 | **100.00343** | 100 | 104857600 |
| Limited View (`src[:100:100]`) | 100.00520 | 100.00509 | 100.00509 | **100.00512** | 100 | 100 |
| Copy (`make` + `copy`) | 0.00521 | 0.00520 | 0.00012 | **0.00351** | 100 | 100 |

### Additional heap evidence

- View: `retained.heap_inuse - baseline.heap_inuse` = **100 MiB** in all three runs.
- Limited View: same **100 MiB** retained inuse delta in all three runs, despite `cap=100`.
- Copy: **0 MiB** retained HeapInuse delta in all three runs (span-granularity aggregate, **not** evidence that the 100-byte copy allocated nothing).
- After setting the controlled root to `nil`, `released.heap_alloc - baseline.heap_alloc` remained within approximately **0.008–0.018 MiB** in every run. Small positive residuals arise from runtime/profiler work and need not equal zero.
- Result length was `100` throughout; capacities were `104857600` for View and `100` for both Limited View and Copy.

### Retained heap profiles (`inuse_space`)

All **six** View/Limited View profiles identify **100 MB (pprof output unit)** of live allocation at `main.makeResult`. No such 100 MiB-size live allocation appears in the three Copy profiles. This is consistent with the HeapAlloc/HeapInuse measurements and independently separated process runs.

Important nuance: a pprof stack identifies the allocation site; it does not directly trace which reference owns an object. The controlled source and root lifecycle are necessary to establish the retention explanation. Absence of a sampled 100-byte copy is not proof of zero allocation.

## Experiment C — Local operation benchmark

Benchmark timing covers View/Copy prefix operations against a shared live 100 MiB input. The source creation and initialization occur outside the timed loops. These measurements characterize local operation cost, **not** the source's reclaimability.

| Operation | Five repeats (ns/op) | Mean ns/op | B/op | allocs/op |
| --- | --- | ---: | ---: | ---: |
| View | 1.712, 1.680, 1.688, 1.697, 1.730 | **1.701** | 0 | 0 |
| LimitedView | 1.730, 1.701, 1.697, 1.697, 1.722 | **1.709** | 0 | 0 |
| Copy | 29.930, 29.860, 28.500, 31.850, 31.390 | **30.306** | 112 | 1 |

Copy reports **112 B/op and 1 alloc/op** with an average of **30.306 ns/op**. View and Limited View report 0 B/op and 0 allocs/op in this specific benchmark. At ~1–2 ns/op for View, minor differences are not robust performance rankings across machines/Go releases.

## Caveats

1. The proof constructs a controlled lifetime scenario. If any other owner holds the source, a 100-byte copy alone cannot make that source collectible.
2. The Copy path first allocates the entire 100 MiB source: **peak allocation during construction is not 100 bytes**. It reduces retained live heap after the original source lifetime ends.
3. `HeapAlloc`, `HeapInuse`, `B/op`, heap profiles and RSS have different meanings. The benchmark does not measure retention and this report makes no claim about RSS release.
4. Heap profile samples are estimates (`MemProfileRate=524288`). Large retained allocations were consistent in all six view profiles; smaller runtime samples vary.
5. Each mode triggers explicit GCs to isolate reachability and uses synthetic bytes; natural service GC timing, P95/P99 and throughput were not measured.
6. Linux virtual CPU scheduling, 4-core CPU quota and 4 GiB memory cap constrain broader performance inference. Comparison to Windows is mechanism-based, not hardware ranking.
7. The sandbox's pprof frontend is Go 1.23.2, older than the Go 1.26.9 program that generated the profiles; all nine were readable, but the profile reader version should be recorded.
8. The compiled test binary reports Go 1.26.9 and a matching build manifest; the application binary also reports **`vcs.modified=true`**. Until the build-time working-tree diff is independently verified, do not claim the binary came from a perfectly clean commit.

## Conclusion

**Mechanism verified on Linux Go 1.26.9.** A 100-byte View or Limited View kept the 100 MiB allocation reachable after GC, while the independent Copy permitted the large source allocation to be collected, under the stated controlled ownership conditions. The extra local cost of Copy was 112 B/op, 1 alloc/op, with approximately 30 ns/op of elapsed computation in this microbenchmark.

Both Linux and Windows measurements support the same mechanism, while the limits of microbenchmarks, controlled lifetimes and runtime memory accounting remain essential.

**Classification: Mechanism verified in two environments; local copy cost measured; production benefit untested.**
