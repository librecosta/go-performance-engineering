## Purpose

Demonstrate, under a controlled Go heap lifecycle, that:

1. A 100-byte `[]byte` view into a 100 MiB allocation can keep the entire backing array reachable.
2. Restricting capacity with `large[:100:100]` does **not** release the source allocation.
3. Making an independent 100-byte copy permits the source allocation to become unreachable when no other owner retains it.
4. The copy has a measurable local allocation and runtime cost; that cost must be considered separately from retained live heap.

This is a mechanism proof and microbenchmark, not a production throughput improvement claim.

## Configuration and procedure

All retention runs use the same experiment CLI, but each mode is executed in a **new OS process**. The CLI allocates and initializes the source in `main.makeResult`, retains only its resulting prefix in a controlled global root, forces two GCs for each heap snapshot, and writes a retained heap profile before clearing the root. Its three snapshots are named `baseline`, `retained`, and `released`. The result is consumed through a checksum and a `runtime.KeepAlive` boundary.

Representative Windows commands from the proof directory:

```powershell
# Build once from the shared proofs module.
go build -o ./results/retention.exe ./cmd/retention

# Run each mode in a separate process; repeat each three times.
cmd.exe /d /c ".\results\retention.exe -mode view -size-mib 100 -keep-bytes 100 -profile results\formal-win-go1269-fixed\view-1.heap.pprof > results\formal-win-go1269-fixed\view-1.json"
cmd.exe /d /c ".\results\retention.exe -mode cap -size-mib 100 -keep-bytes 100 -profile results\formal-win-go1269-fixed\cap-1.heap.pprof > results\formal-win-go1269-fixed\cap-1.json"
cmd.exe /d /c ".\results\retention.exe -mode copy -size-mib 100 -keep-bytes 100 -profile results\formal-win-go1269-fixed\copy-1.heap.pprof > results\formal-win-go1269-fixed\copy-1.json"
```

The loop over repetitions 1–3 uses the same flags and unique file names. Each profile was inspected using:

```powershell
go tool pprof -top -inuse_space ./results/formal-win-go1269-fixed/view-1.heap.pprof
```

The baseline / retained / released heap deltas are computed **within each process**, not by comparing unrelated absolute heap totals.

## Experiment A/B — Retained live heap

`HeapAlloc retained - baseline`, expressed in MiB, for the three independent process runs:

| Mode | Run 1 | Run 2 | Run 3 | Mean | `len` | `cap` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| View (`src[:100]`) | 100.005 | 100.005 | 100.005 | **100.005** | 100 | 104857600 |
| Limited view (`src[:100:100]`) | 100.005 | 100.005 | 100.005 | **100.005** | 100 | 100 |
| Copy (new backing array) | 0.00498 | 0.00497 | 0.00509 | **0.00501** | 100 | 100 |

These values were computed from the integer-byte `heap_alloc` fields, without modifying or reconstructing any rows.

### Additional heap evidence

- In both View and Limited View, `retained.heap_inuse - baseline.heap_inuse` was exactly **100 MiB** in all three runs.
- In Copy, `retained.heap_inuse - baseline.heap_inuse` was **0 MiB** in all three runs (this is an aggregate, span-granularity metric; it does not imply that the 100-byte copy did not allocate).
- In View and Limited View, `released.heap_alloc - baseline.heap_alloc` was only approximately 19 KiB after clearing the retaining root and collecting. Copy released snapshots varied by approximately 24 KiB over baseline. These small positive values include normal runtime/profiling overhead and should not be expected to equal zero.
- All nine corrected JSON files passed strict JSON parsing. Every run has `source_bytes=104857600`, `keep_bytes=100`, `len=100`, and a matching result checksum of **12838**.

### Retained heap profiles (`inuse_space`)

All three View profiles attribute **100 MiB** of live allocation to `main.makeResult`; all three Limited View profiles do the same. None of the three Copy profiles shows that retained 100 MiB allocation.

The Copy profiles still contain smaller samples from Go runtime / initialization work (roughly 1.5–2.6 MB sampled total); the absence of a 100-byte sample is not, by itself, proof of collection. The controlled root lifecycle and the heap delta supply the stronger evidence.

A pprof stack reports the **allocation site**, not a reference-retention path. The ownership conclusion additionally relies on the controlled source code and independent-process design.

## Experiment C — Local operation benchmark

Command used to produce the saved text result:

```powershell
go test -run '^$' -bench '^BenchmarkPrefix$' -benchmem -benchtime=1s -count=5 . -args -bench-size-mib=100
```

The benchmark initializes one 100 MiB source outside the timed loops, keeps it reachable through the test, and calls each prefix implementation on that shared input. These numbers measure **operation cost**, not whether the large source could be reclaimed.

| Operation | Five runs (ns/op) | Mean ns/op | B/op | allocs/op |
| --- | --- | ---: | ---: | ---: |
| View | 1.670, 1.662, 1.573, 1.642, 1.535 | **1.616** | 0 | 0 |
| Limited view | 1.541, 1.538, 1.544, 1.532, 1.567 | **1.544** | 0 | 0 |
| Copy | 25.76, 27.08, 27.93, 29.58, 26.51 | **27.372** | 112 | 1 |

In this narrow benchmark, Copy adds one reported heap allocation (112 B/op) and a small per-operation time cost. The View / Limited View difference is tiny and should not be interpreted as a robust general performance ranking. Nanosecond-scale measurements are sensitive to compiler and test-harness context.

## Caveats

1. This is a constructed lifetime example: if another live reference owns the large source, Copy alone will not make the source collectible.
2. The Copy case still allocates and initializes the full source first, so its **peak** memory during construction is not 100 bytes. It reduces *retained* live memory after source lifetime ends.
3. `HeapAlloc` measures allocated Go heap objects; `HeapInuse` measures space in occupied spans; `B/op` measures allocation traffic. None is process RSS.
4. The Go heap profile uses sampling (`MemProfileRate=524288`), and its small-object totals are approximate. The large live allocation is consistently visible in six matching profiles.
5. Explicit GC and synthetic workloads were chosen to isolate the ownership mechanism; this does not measure natural GC timing, total memory budget, service P95/P99, or production throughput.
6. The user machine and Go 1.26.9 are the measurement scope. Linux reproduction and broader version comparisons are pending.
7. Corrected JSON data was obtained by **rerunning** the scenario, not editing old broken records. The old malformed JSON files must not be cited as valid input data.
8. The original saved profiles may embed a private local build path in pprof metadata. Redact machine-specific paths before redistributing raw artifacts publicly. This public report uses relative paths only.

## Conclusion

**Mechanism verified on Windows Go 1.26.9.** The three view modes produced consistent checksum results but radically different retained-heap footprints: sharing either unrestricted or capacity-limited views retained a 100 MiB backing allocation; an independent 100-byte copy allowed the large source allocation to be reclaimed. In the controlled hot-prefix benchmark, the copy cost was 112 B/op, 1 alloc/op, and a mean 27.372 ns/op.

This is an ownership / lifetime trade-off, **not** a blanket recommendation to copy slices. Prefer views when shared backing storage and lifetime semantics are appropriate. Copy short long-lived views when the source is much larger, temporary, and otherwise no longer needed; validate with representative application workloads.

Classification: **Mechanism verified. Local copy cost measured. Production benefit untested.**
